一、架构与设计模式（高频必问）
------------------------------------------------------------------------

Q1：项目用了什么架构？为什么选这个？

项目采用 MVVM + Repository 模式：
- View 层：Activity 负责 UI 展示和用户交互
- ViewModel 层：MainViewModel、BlindHomeViewModel 持有 StateFlow，
  UI 通过 collect 响应式订阅数据变化
- Model/Repository 层：RunningRepository 封装了 Room（本地）和 Retrofit（远程）
  两个数据源，对外暴露统一接口

选择理由：
1. ViewModel 生命周期独立于 Activity，转屏不丢数据
2. StateFlow 是 Kotlin 协程原生响应式方案，比 LiveData 更轻量
3. Repository 模式实现了单一数据源原则——UI 不关心数据来自本地还是网络

追问：为什么不用 MVP？
MVP 的 Presenter 需要持有 View 引用，容易内存泄漏，且需手动管理生命周期。
MVVM 通过 ViewModel + 数据绑定解耦更彻底。

------------------------------------------------------------------------

Q2：Repository 里 getRecords() 的 forceRefresh 参数，是哪种缓存策略？

这是 Cache-Aside（旁路缓存）策略的变体——本地优先（Local-first）：

suspend fun getRecords(forceRefresh: Boolean = false): List<RunningRecord> {
    val localRecords = runningRecordDao.getRecordCount()
    return if (forceRefresh || localRecords == 0) {
        // 缓存未命中或强制刷新 → 远程拉取 → 写入本地
        val posts = apiService.getPosts()
        val entities = posts.map { it.toEntity() }
        runningRecordDao.insertAll(entities)
        entities.map { it.toDomainModel() }
    } else {
        // 缓存命中 → 直接返回本地数据
        runningRecordDao.getAllRecordsRaw().map { it.toDomainModel() }
    }
}

追问：为什么不直接用网络数据？
视障用户可能在弱网环境跑步，本地优先保证离线可用。网络数据作为补充同步源。

------------------------------------------------------------------------

Q3：Room 和原生 SQLite 的区别？怎么防 SQL 注入？

Room 是 Google 官方的 SQLite 抽象层：
- 编译期校验 SQL 语法——原生 SQLite 只有运行时才知道 SQL 写错了
- @Query 注解在编译时通过 KSP 生成实现类，参数自动绑定为 ? 占位符
  → 这是参数化查询，天然防 SQL 注入

@Query("SELECT * FROM users WHERE phone = :phone LIMIT 1")
suspend fun getUserByPhone(phone: String): UserEntity?

:phone 会被 Room 编译成 PreparedStatement.setString()，用户输入不可能逃逸出字符串边界。

追问：如果不用 Room 怎么防注入？
必须用 rawQuery + selectionArgs 数组传参，或 compileStatement 绑定参数，
严禁字符串拼接 SQL。

------------------------------------------------------------------------

Q4：lifecycleScope.launch 和普通 Thread 有什么区别？

Kotlin 协程的结构化并发：
1. 自动取消：Activity onDestroy 时 lifecycleScope 自动取消所有子协程
2. 线程切换：withContext(Dispatchers.IO) 在 IO 线程执行数据库操作，
   withContext(Dispatchers.Main) 回到主线程更新 UI
3. 异常传播：协程内异常被结构化捕获，不会像裸线程那样静默死亡

对比：
// 协程
lifecycleScope.launch {
    val data = withContext(Dispatchers.IO) { dao.query() }  // IO 线程
    textView.text = data.toString()  // 自动回 Main 线程
}

// 传统
Thread {
    val data = dao.query()
    runOnUiThread { textView.text = data.toString() }
}.start()


二、数据持久化（必问）
------------------------------------------------------------------------

Q5：SharedPreferences 和 SQLite 分别存什么？为什么不用一个？

| 数据类型           | 存储方式           | 原因                             |
|-------------------|-------------------|----------------------------------|
| 登录状态、用户偏好   | SharedPreferences | 键值对，量小，读写频繁              |
| 跑步记录、用户档案   | Room/SQLite       | 结构化数据，需要排序/筛选/聚合查询     |

SharedPreferences 是 XML 文件，全量加载到内存。存上千条跑步记录每次都要解析整个 XML，
不可接受。SQLite 有 B-Tree 索引，百万条记录也能毫秒级查询。

追问：commit() 和 apply() 区别？
commit() 同步写入磁盘，返回 Boolean，会阻塞当前线程。
apply() 异步写入内存 + 后台刷盘，无返回值。项目中全部用 apply() 避免 ANR。

------------------------------------------------------------------------

Q6：数据库版本从 v1 升到 v7，怎么做迁移的？

Room 的 Migration 对象定义每个版本的 SQL 变更：

val MIGRATION_6_7 = object : Migration(6, 7) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE users ADD COLUMN examPassed INTEGER NOT NULL DEFAULT 0")
        db.execSQL("ALTER TABLE users ADD COLUMN examScore INTEGER NOT NULL DEFAULT 0")
    }
}

迁移原则：
- 只用 ALTER TABLE ADD COLUMN，绝不 DROP TABLE
- 新列必须有 DEFAULT 值，确保旧数据兼容
- 添加迁移后更新 @Database(version = 7) 并传入 .addMigrations()

追问：fallbackToDestructiveMigration 是什么？
销毁所有数据重建数据库。项目早期用了这个方法——升级时用户数据全丢。
后来改成了正确的迁移链。


三、Android 框架机制
------------------------------------------------------------------------

Q7：Foreground Service 和普通 Service 的区别？为什么用前台 Service？

|              | 普通Service       | 前台Service                              |
|--------------|-------------------|------------------------------------------|
| 通知栏        | 无                | 必须有常驻通知                              |
| 系统回收策略   | 高内存压力下被kill  | 几乎不会被kill                              |
| 适用场景      | 短时后台任务        | 用户可感知的持续任务                          |

跑步计时是用户正在进行的、需要持续感知的任务，必须用前台 Service。
startForeground(1001, notification) 必须在 onStartCommand 的 5 秒内调用。

保活手段：
1. IMPORTANCE_HIGH 通知渠道
2. START_STICKY 被杀后自动重启
3. FOREGROUND_SERVICE_IMMEDIATE 行为标志（Android 12+）
4. FLAG_KEEP_SCREEN_ON 保持屏幕唤醒

------------------------------------------------------------------------

Q8：你申请了哪些运行时权限？为什么按需申请？

- ACCESS_FINE_LOCATION：仅在地图选点界面申请，跑步页面使用地图 SDK 内部定位不额外申请
- POST_NOTIFICATIONS（Android 13+）：前台 Service 必须发通知
- VIBRATE：紧急求助和按钮反馈的正常运行时权限

原则是最小权限 + 按需申请：
1. 用户不进地图选点，就不弹位置权限
2. 拒绝了权限也不影响核心功能——地图降级为手动拖动+文字输入
3. 每次申请前先 TTS 语音说明用途

------------------------------------------------------------------------

Q9：dispatchKeyEvent 拦截音量键的原理？

dispatchKeyEvent 是 Activity 的事件分发入口，所有按键事件先到这里再传给子 View：

override fun dispatchKeyEvent(event: KeyEvent): Boolean {
    if (event.keyCode == KeyEvent.KEYCODE_VOLUME_UP) {
        when (event.action) {
            KeyEvent.ACTION_DOWN -> { /* 记录按下时间，启动3秒计时 */ }
            KeyEvent.ACTION_UP   -> { /* 松手，判断是否>=3秒 */ }
        }
        return volumeLongPressFired  // 长按触发时消费事件，短按交给系统
    }
    return super.dispatchKeyEvent(event)
}

关键设计：
- 短按不拦截：返回 super.dispatchKeyEvent()，音量正常调节
- 长按消费：返回 true，阻止音量条弹出，触发紧急拨号

追问：后台怎么拦截？
Activity 的 dispatchKeyEvent 只在应用前台有效。后台/锁屏场景用了
AccessibilityService——系统级无障碍服务可以全局拦截按键事件。

之前试过 ACTION_MEDIA_BUTTON 广播接收器——这条路走不通，
因为音量键不产生媒体按钮广播。


四、计算机基础理论
------------------------------------------------------------------------

Q10：TTS 的音频延迟怎么控制？为什么用 STREAM_MUSIC？

- AudioAttributes.USAGE_ASSISTANCE_ACCESSIBILITY：系统给更高优先级和更低延迟
- STREAM_MUSIC：音量与媒体音量同步，用户用音量键直接调整 TTS 音量
- 跑步播报用 QUEUE_FLUSH 模式——直接打断当前播报，不排队

追问：为什么小米手机没声音？
小米 MIUI 的音频焦点管理比 AOSP 更严格。需要额外调用
AudioManager.requestAudioFocus() 获取音频焦点，否则 TTS 有输出但音量被压到静音。
另外需要消除双重 TTS 实例冲突（Service 和 TtsHelper 各有一个）。

------------------------------------------------------------------------

Q11：DiffUtil 的算法复杂度？为什么比 notifyDataSetChanged 好？

DiffUtil 基于 Myers 差分算法，时间复杂度 O(N + D²)，N=列表长度，D=最小编辑距离：
- 列表无变动：D ≈ 0，复杂度接近 O(N)
- 最坏情况：D ≈ N，复杂度 O(N²)

notifyDataSetChanged() 会触发所有可见 item 的 onBindViewHolder（包括内容完全没变的），
且没有任何动画。ListAdapter + DiffUtil 只刷新变化的 item，自动附带插入/删除/移动动画。

areItemsTheSame() 通过 ID 比较，areContentsTheSame() 通过 data class 的 equals()。

------------------------------------------------------------------------

Q12：data class 和普通 class 有什么区别？

Kotlin 的 data class 编译器自动生成：
1. equals() / hashCode() —— 基于主构造函数的所有属性
2. toString() —— "类名(属性=值)" 格式
3. copy() —— 浅拷贝，可修改部分字段
4. componentN() —— 解构声明支持

DiffUtil 的 areContentsTheSame() 直接依赖 data class 的 equals()。

一、项目管理与协作
------------------------------------------------------------------------

Q15：两个人在一个 Git 仓库里协作，怎么避免代码冲突？

1. 模块拆分天然解耦：一人负责 ui/blind/ + data/util/，另一人负责 ui/volunteer/ + server/
2. 接口先行约定：改 ApiService 或 DAO 等公共接口时先口头对齐方法签名
3. 分支策略：master 主分支保持可编译；功能在各自分支开发，完成后 Merge
4. Android Studio 内置 Git 工具：提交前可视化 diff，确认无误再 push

Q16：项目总共写了多少代码？

估算：
- Kotlin 源码：约 40 个文件，~4500 行
- XML 布局：约 25 个文件，~3000 行
- Drawable 资源：约 10 个文件
- 服务器模块：约 3 个 Kotlin 文件，~250 行

可以用 git log --shortstat --author="名字" 看每人增删行数。
但代码行数不是衡量工作量的好指标——一段 10 行的数据库迁移可能比 100 行的布局难得多。


二、测试与质量保障
------------------------------------------------------------------------

Q17：你写测试了吗？怎么保证代码质量？

MVP 阶段没有系统写单元测试。但做了四层质量保障：

| 方式         | 具体做法                                              |
|-------------|------------------------------------------------------|
| 编译期校验    | Room @Query 在编译时检查 SQL 语法，写错就编译不过         |
| 真机验证     | 小米 13 实机跑过全部流程：登录→发布→接单→跑步→保存记录    |
| Log 追踪     | 所有 catch 块有 Log.e(TAG, msg, e)，关键路径有 Log.d     |
| 边界防护     | isNotEmpty() 检查空字符串、?.let 空安全、getOrNull 防越界 |

追问：如果要加测试会加哪几种？
1. 单元测试：RunningRecord.toEntity() ↔ toDomainModel() 映射函数
2. Room DAO 测试：@RunWith(AndroidJUnit4::class) + 内存数据库，验证 SQL 查询正确性
3. UI 测试：Espresso + TalkBack，验证无障碍朗读顺序和按钮点击

Q18：内存数据库和真机数据库有什么区别？测试时怎么隔离？

Room 支持创建内存数据库用于测试：
val testDb = Room.inMemoryDatabaseBuilder(context, AppDatabase::class.java).build()
val realDb = Room.databaseBuilder(context, AppDatabase::class.java, "blind_runner_db").build()

区别：
- 内存数据库没有 Migration 要求——每次 version=最新
- 内存数据库查询速度远快于文件数据库
- 用 @Rule 在每个测试方法前创建、后销毁，保证测试隔离


三、Kotlin 语言特性
------------------------------------------------------------------------

Q19：object 关键字和 class 有什么区别？

Kotlin 的 object 是单例模式的语言级实现：

object TtsHelper : TextToSpeech.OnInitListener { ... }
object AppPrefs { ... }
object RetrofitClient { ... }

编译器生成的 Java 等价代码：
public class TtsHelper {
    private static volatile TtsHelper instance;
    private TtsHelper() {}
    public static TtsHelper getInstance() {
        if (instance == null) {
            synchronized (TtsHelper.class) {
                if (instance == null) instance = new TtsHelper();
            }
        }
        return instance;
    }
}
// Kotlin 一行 object TtsHelper { ... }  =  Java 十几行手写单例

------------------------------------------------------------------------

Q20：sealed class 和 data class 怎么用？

data class —— 用于数据载体（RunningRecord、UserEntity），编译器自动生成
equals/hashCode/toString/copy/componentN。DiffUtil 靠 equals 判断内容变化。

sealed class —— 用于有限状态：
sealed class DemandStatus {
    object Pending : DemandStatus()
    object Accepted : DemandStatus()
    object Completed : DemandStatus()
    object Cancelled : DemandStatus()
}

好处：when 表达式不需要 else 分支——编译器能穷举所有状态，
遗漏任何一个编译器会报错。

追问：项目里为什么没实际用 sealed class？
状态存在 SQLite 里是 String 类型（"pending"/"accepted"等），
从数据库读回来时类型信息已丢失。MVP 阶段为了简洁用字符串匹配。


四、异常与边界处理
------------------------------------------------------------------------

Q21：如果用户的手机没有安装 TTS 引擎怎么办？

TtsHelper.onInit() 返回三种状态码：

| status             | 含义                   | 处理                              |
|--------------------|-----------------------|-----------------------------------|
| SUCCESS            | 引擎可用               | 正常播报                           |
| LANG_MISSING_DATA  | 引擎安装了但没中文包     | 尝试 SIMPLIFIED_CHINESE，再失败用默认 |
| ERROR              | 没有 TTS 引擎          | 2秒后重试一次，仍失败则静默降级        |

追问：用户怎么知道 TTS 有问题？
设置页面切换语音开关时 TtsHelper.speak("语音播报功能正常...")，
用户听不到自然会检查 TTS 引擎设置。

------------------------------------------------------------------------

Q22：跑步中接电话会怎样？GPS 信号丢失呢？

接电话：
- Service 不会被杀——IMPORTANCE_HIGH + FOREGROUND_SERVICE_IMMEDIATE 保证
- GPS 会临时失去精度但不会停止——系统自动降级到网络定位
- TTS 播报会被来电铃声中断——这是系统行为，优先级高于无障碍音频

GPS 信号丢失：
- RunningModeActivity 有 10 秒超时兜底：
  handler.postDelayed({ TtsHelper.speak("定位超时，开始跑步"); startCountdown() }, 10000L)
- 计时和语音播报不依赖 GPS——GPS 只用来画轨迹线和记录距离
- trackJson 字段存 GPS 坐标数组，有信号期间的点都保留


五、安全与隐私
------------------------------------------------------------------------

Q23：用户数据在手机上是明文存还是加密存？

| 数据类型           | 存储位置                 | 是否加密 | 说明                                 |
|-------------------|------------------------|---------|--------------------------------------|
| 跑步记录           | Room SQLite            | 明文    | 不包含敏感个人信息                      |
| 手机号             | Room + SharedPreferences| 明文   | 需要用于数据隔离和登录标识               |
| 紧急联系人电话       | SharedPreferences      | 明文    | 紧急求助时需立即读取，加密会引入延迟       |
| 验证码             | SharedPreferences      | 明文    | 5分钟过期，用完即标记失效                |
| 密码（旧方案）       | SharedPreferences      | 明文 ❌ | 已废弃，现在是纯验证码登录               |

现阶段没有加密——因为数据全部在本地，不上传。服务端上线后，密码/验证码用 bcrypt 哈希存储。

追问：bcrypt 和 MD5 有什么区别？
MD5 是快速哈希——GPU 可以每秒算几十亿次，彩虹表秒破。
bcrypt 自带 salt + 可配置迭代次数（cost factor），故意很慢（约 100ms 一次），
暴力破解成本极高。

------------------------------------------------------------------------

Q24：有没有想过 App 被坏人利用怎么办？

三条防线：
1. 紧急求助不自动拨号——防止恶作剧恶意拨出骚扰电话，必须用户手动点拨号键确认
2. 考核门槛——志愿者必须通过 80 分考核才能看到视障用户的联系方式，
   防止随便注册一个账号获取视障用户的手机号
3. 需求接单后双向可见——接单后双方才看得到对方联系方式，
   且接单操作有二次确认弹窗，防止误触暴露隐私

七、开放性问题
------------------------------------------------------------------------

Q26：这个项目最大的技术挑战是什么？

最大的挑战是 TTS 在小米手机上的无声问题。调试过程：
1. 模拟器有声 → 排除代码逻辑错误
2. 卸载其他 App → 排除音频焦点被占
3. 加 UtteranceProgressListener → onStart 触发了说明引擎在工作，但硬件没输出
4. 查 Android 文档 → Android 10+ 要求 AudioAttributes
5. 加 USAGE_ASSISTANCE_ACCESSIBILITY → 仍无声
6. 查小米开发者论坛 → MIUI 需要显式 requestAudioFocus()
7. 加 AudioFocusRequest → 终于有声

教训：模拟器验证 ≠ 真机验证，厂商 ROM（尤其是小米 MIUI）对 AOSP 的改动往往不在官方文档里。

Q27：如果重新做这个项目，会怎么改进架构？

1. Jetpack Compose 替代 XML 布局——声明式 UI 更适合无障碍适配

Q28：为什么不用服务器？

服务器代码其实已经写好了，在项目 server/ 模块里，用 Ktor + H2 搭建了完整后端，
12 个 API 端点（登录/注册/需求CRUD/跑步记录/考核/排行榜）。
MVP 阶段暂时注释掉，优先本地开发。

三个原因：
1. 跑步场景离线可用性要求极高——不能因为网络波动导致计时中断或求助失败
2. Local-first 策略——所有核心操作先落本地 SQLite，网络同步是异步补充
3. 渐进式开发——先把客户端核心闭环跑通，再接入服务器

架构已留好切换接口：RetrofitClient.setServerUrl() 改一行配置就能连上服务器。

------------------------------------------------------------------------

Q29：切换到服务器模式后数据怎么同步？

采用最终一致性模型：
- 本地 Room 是唯一写入入口——用户操作立即写入本地返回成功
- 后台通过 remoteId 字段追踪同步状态：null=未同步，有值=已同步
- 重试机制用指数退避算法，失败不阻塞新操作
- 冲突处理以时间戳较新的数据为准
