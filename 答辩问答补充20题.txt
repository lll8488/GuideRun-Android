                 助盲跑 App 答辩问答 — 补充 20 题
================================================================================

1. 你做的部分和别人做的部分怎么对接？有没有出现过接口对不上的情况？
------------------------------------------------------------------------
答：我们约定了一个"接口先行"的开发方式。比如我要做一个发布需求的功能，需要他把
RunningRecordDao 里的 insert 方法写好，他就先把 DAO 接口定义出来：

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insert(record: RunningRecordEntity): Long

然后我直接调用这个方法，不用等他实现。Room 会在编译时检查 SQL 是否正确。
如果字段对不上——比如他加了新字段但我没传——Kotlin 编译直接报错，不会留到运行时才发现。

唯一一次接口对不上是 SharedPreferences 的 key 名写错了——"profile_name" vs "profileName"，
花了十分钟排查，后来我们统一用下划线命名。


2. 你们这个项目能不能上架应用商店？有什么门槛？
------------------------------------------------------------------------
答：技术上可以。但上架需要：
1. 应用签名——要用正式的 keystore，不能用 debug 签名
2. 隐私政策——我们的隐私政策已经在 SettingsActivity 里可以查看
3. 权限声明——Google Play 要求说明每个权限的用途。我们只有三个运行时权限，
   每个都有明确用途
4. 无障碍服务声明——EmergencyAccessibilityService 需要向 Google 提交审核，
   说明用途是"跑步安全场景下的紧急求助"
5. 目标 API 级别——当前 targetSdk=34，符合 Google Play 要求

最大的门槛其实是内容审核——我们的"验证码"是模拟的，审核人员会认为功能不完整。
接入真实短信服务后才能过审。


3. 你这 App 的包体积多大？怎么优化？
------------------------------------------------------------------------
答：Debug 包约 30MB，主要占用：
- 高德地图 3D SDK：约 12MB（.so 文件）
- Kotlin 标准库 + AndroidX + Room + Retrofit：约 10MB
- 资源文件（layout/drawable）：约 3MB

优化方案：
1. 开启 R8 混淆——可减少约 40% 代码体积
2. 用 App Bundle（.aab）代替 APK——Google Play 按设备分发，用户只下载对应 CPU 架构的 .so
3. 地图 SDK 换成 2D 版本——减少约 5MB，但失去 3D 效果
4. 用矢量图（VectorDrawable）替代多套 PNG——一套 xml 适配所有分辨率


4. 盲人用户怎么找到这个 App？图标和名字有讲究吗？
------------------------------------------------------------------------
答：App 名字"助盲跑"——三个字，简单直接。TalkBack 朗读时读作"助盲跑"，
不会读成英文或其他乱码。图标我们用了深绿色背景+白色跑步人物剪影——
高对比度，低视力用户也能辨识。启动页也用了白字绿底的品牌标识，
Splash 页面有 TalkBack 朗读："助盲跑，让每一次奔跑都有陪伴"。


5. 你们的代码有没有用过 ChatGPT 或者 AI 辅助？
------------------------------------------------------------------------
答：用过。但 AI 写的代码不能直接用——需要检查三点：
1. 是否符合 PRD 要求——AI 不知道我们产品的具体规范，比如"不能自动拨号"这条红线
2. 是否有内存泄漏——AI 经常漏掉 Handler 清理、TTS shutdown
3. 无障碍是否完整——AI 写的代码往往没有 contentDescription

我们的 TTS 工具类的初版是 AI 生成的，但小米无声问题是我们自己排查解决的。
数据库迁移脚本也是自己手写的——AI 不知道之前的版本结构。


6. 如果盲人在跑步中手机不小心锁屏了，语音播报还会继续吗？
------------------------------------------------------------------------
答：会的。三件事保证：
1. 屏幕常亮——RunningModeActivity 用 FLAG_KEEP_SCREEN_ON 防止自动锁屏
2. 即使锁屏——前台 Service 依然运行，计时和播报不中断
3. 通知栏常驻——锁屏界面可以看到"助盲跑进行中 00:32:45 · 2.80km"

如果用户主动按了电源键锁屏，Service 机制保证后台继续运行。


7. 前台 Service 在 Android 14 上有什么变化？
------------------------------------------------------------------------
答：Android 14 要求前台 Service 必须声明 service type。我们在 Manifest 里写了：

    <service android:name=".service.RunningService"
        android:foregroundServiceType="dataSync|location" />

如果没有声明 type，在 Android 14 上 Service 会启动失败。
我们声明的两个 type：
- location——跑步轨迹需要 GPS
- dataSync——未来同步跑步记录到服务器

另外 Android 14 还要求 POST_NOTIFICATIONS 权限才能发通知，
我们也在 Manifest 里声明了。


8. 你们这个 App 对老年人友好吗？
------------------------------------------------------------------------
答：友好——但我们的设计目标不是老年人，是视障用户。不过两者有重叠：
1. 按钮最大 80dp 高、最小 48dp——手指不灵活也能点到
2. 文字够大——核心数字（计时器）52sp，标题 26sp
3. 语音播报——不用看屏幕也能用
4. 高对比度主题——老花眼也能看清黑白界面

如果真的面向老年人，还需要加一个功能：播报语速可调。当前语速是 1.0 倍，
老年人可能需要 0.7 倍慢速。


9. 为什么不直接做成微信小程序，要做 App？
------------------------------------------------------------------------
答：三个原因：
1. 前台 Service 保活——小程序没有这个能力，切到后台几分钟就被微信杀掉了，
   跑步计时根本没法做
2. TextToSpeech——小程序只能用微信内置的语音 API，无法控制音频焦点、
   无法适配小米等厂商的 TTS 引擎
3. 音量键长按紧急求助——小程序无权拦截系统按键

小程序适合轻量工具，我们的需求（跑步保活+语音播报+按键监听）必须原生 App 才能做。


10. 你的数据库用的是 Room，能不能直接用文件存数据？
------------------------------------------------------------------------
答：技术上可以——比如存成 JSON 文件。但有几个问题：
1. 查询慢——要找"138 开头手机号的所有跑步记录"，JSON 文件需要全部读出来遍历，
   SQLite 有索引，毫秒级
2. 并发写——如果跑步中存轨迹点，同时又要查历史记录，文件可能写坏。
   SQLite 有 WAL（Write-Ahead Logging）模式，支持并发读写
3. 数据迁移——添加新字段时，JSON 需要遍历每条数据去加默认值。
   Room 的 Migration 直接 ALTER TABLE，一行 SQL 搞定


11. 你们的验证码是 6 位数字，为什么不用 4 位？
------------------------------------------------------------------------
答：6 位数字有 100 万种组合，4 位只有 1 万种。对于安全场景（涉及用户手机号）来说，
6 位更安全。而且视障用户输入验证码时用的是 TalkBack 屏幕阅读器——
输入位数少反而容易误触确认按钮。6 位需要用户多输入两个数字，
多了一步确认的时间窗口。


12. 紧急求助为什么不直接用 110？
------------------------------------------------------------------------
答：PRD 要求的是"拨打紧急联系人"——因为场景不同：
1. 跑步中轻微受伤——打给家人就好，不需要 110
2. 迷路或路线偏离——打给陪跑志愿者比 110 更合适
3. 真遇到严重事故——用户可以选择打 110

但如果用户没有设置紧急联系人，默认就填 110——EmergencyContactActivity 保存时会提示
"至少填写一位紧急联系人"。我们的设计是：优先第一位紧急联系人，无联系人时降级到 110。


13. 你们怎么保证两个用户身份（视障/志愿者）不会互相看到不该看的功能？
------------------------------------------------------------------------
答：路由层做了身份检查：

    // LoginActivity.navigateToHome()
    if (userType == "volunteer") → VolunteerHomeActivity
    else → BlindHomeActivity

两个首页的功能入口完全不同：
- 视障端：发布需求、开始跑步、历史记录、个人中心
- 志愿者端：待接单、训练营、排行榜、我的接单

身份切换时更新 userType 字段，并且切换后直接跳到目标首页——不会经过登录页。
每个 Activity 启动时都会检查 userType，视障端看不到接单按钮，志愿者端看不到发布需求按钮。


14. 你们的 App 耗电吗？跑步一个小时费多少电？
------------------------------------------------------------------------
答：跑步模式下耗电主要在三个方面：
- GPS 定位：持续追踪，约每小时 5-8% 电量
- 屏幕常亮：约每小时 8-12%（取决于亮度）
- 地图渲染：约每小时 2-4%

总计约 15-25%/小时。优化措施：
1. 跑步模式用暗色背景——AMOLED 屏黑色像素不发光，省电
2. GPS 采样间隔 3 秒——不是每秒都定位
3. 地图只画轨迹线，不加载 3D 建筑模型
4. 如果用户用省电模式，地图会自动降低刷新率


15. 有没有考虑过国际化？外国人用怎么办？
------------------------------------------------------------------------
答：当前所有界面和语音都是中文。如果要支持英文：
1. strings.xml 抽离——我们已经有 strings.xml，但大部分文字还是硬编码在代码和
   XML 里的。需要全部迁移到资源文件
2. TTS 语言切换——Locale.CHINA 改为动态读取用户设置
3. 高德地图的逆地理编码返回的是中文地址，英文需要换 Google Maps 或
   用高德的英文 API

这个没有放在 MVP 里，因为目标用户是国内的中文用户。但架构上 strings 资源化后，
加语言只是时间问题。


16. 如果有 100 个人同时发需求，你的列表会不会卡？
------------------------------------------------------------------------
答：当前 MVP 阶段不会——因为数据纯本地，SQLite 查 100 条记录毫秒级。
但如果接入服务器后，1000 人在线同时刷列表，需要：
1. 分页加载——RecyclerView 滚动到底部时加载下一页，每次 20 条
2. 服务器端用 Redis 缓存热门需求列表，减少数据库查询
3. 列表项用 ListAdapter + DiffUtil——只更新变化的项，不重绘整个列表

我们已经用了 ListAdapter + DiffUtil，本地性能没问题。分页需要服务端配合。


17. 你的代码里有 Design Pattern 吗？举一个例子。
------------------------------------------------------------------------
答：有三个：
1. Repository Pattern——RunningRepository 封装两个数据源，对外暴露统一接口
2. Singleton Pattern——TtsHelper、AppPrefs、RetrofitClient 都用 Kotlin object 实现单例
3. Observer Pattern——ViewModel 的 StateFlow 被 Activity collect 订阅，
   数据变化时自动更新 UI（响应式）

Repository 模式最典型：UI 层调用 repository.getRecords()，不关心数据来自 Room 还是 Retrofit。
如果后续要改数据源——比如从 SQLite 换成服务器——只需要改 Repository 内部，UI 层一行不动。


18. 你这个 App 和其他类似产品比有什么优势？
------------------------------------------------------------------------
答：目前市面上没有专门为视障跑者做的陪跑匹配 App。其他跑步 App（Keep、咕咚）虽然有无障碍
支持，但没有陪跑匹配功能。我们的差异化：
1. 陪跑绳规范考核——保证志愿者不是随便注册就能接单，需要学习+考试
2. 紧急求助专为视障设计——长按物理按键而不是屏幕按钮，跑动中更容易操作
3. 纯语音跑步体验——不需要看屏幕就知道跑了多久多远
4. 陪跑绳引导模式固定标签——所有需求都标注了陪跑绳模式，志愿者一看就知道


19. 你觉得你这个 App 能商用吗？
------------------------------------------------------------------------
答：还差最后一步——接入真实短信验证码服务。除此之外，核心功能闭环已经完整。
商用需要的：
1. 短信服务——阿里云/腾讯云 SMS API，每条 4 分钱左右
2. 服务器部署——Ktor 代码已写好，部署到阿里云 ECS（最低配约 50 元/月）
3. 用户协议和免责声明——跑步有安全风险，需要法律文本
4. 高德地图商用 Key——申请企业认证，获取更高配额

商业模式的话，可以考虑对陪跑志愿者收取少量服务费（类似滴滴的抽成模式），
或者公益基金会赞助运营。


20. 做完这个项目你最大的收获是什么？
------------------------------------------------------------------------
答：两个收获。
技术上——以前只写功能正常的代码，这个项目让我意识到"无障碍"不是可有可无的附加项，
而是从架构阶段就要考虑的设计约束。比如按钮至少要 48dp——如果一开始没规划，
后面要改几十个 layout 文件。再比如 TTS 的生命周期管理，差点在小米手机上翻车。

产品上——PRD 里的每一条规定背后都有一个真实的用户场景。比如"紧急求助不能自动拨号"，
一开始觉得多此一举，后来理解了：视障用户跑步时可能会误触，自动拨出会造成恐慌和骚扰。
好的产品设计不是炫技，是理解用户。
